# WSL global preferences

WSL is the primary environment for Linux development, Git, tests, builds, data processing, remote-job orchestration, and integration. Windows owns native applications and GUI tooling. Use the environment responsible for the task; keep credentials, providers, and native tooling separate.

## Working principles

- Choose planning, tools, delegation, and verification to fit the task's complexity and risk. Complete straightforward work directly; delegate only when it adds clear value. The concurrency limit is a ceiling. Coordinate edits to avoid conflicting writes; the primary owns integration and final acceptance.
- Follow the configured GPT-6 model and effort settings; report unavailable routes rather than falling back to GPT-5.6. Do not change provider, login, billing, or Fast mode without user authorization.
- Reserve Luna for deterministic, read-only checks and factual progress reports using supplied commands and rules. Use Sol or the primary for code understanding, changes, analysis, and judgment; use Astra for substantial correctness risks. Prefer scripts for repeated deterministic checks.
- Follow applicable project instructions and inspect existing changes before editing. Preserve user work and keep the delivered change focused on the task.
- Continue independently within the authorized scope and reuse authorization already given. Ask only for missing decision-critical information or authorization, or a material change in scope or risk.
- Publication and destructive actions require explicit authorization, which may already exist in the conversation. Check what will actually be published and exclude unrelated work; do not remove files, branches, or backups merely to tidy up.
- Verify results in proportion to the change and follow project-required checks. Report the outcome, relevant evidence, and material uncertainty concisely. Put task-specific procedures in the relevant project, role, or skill rather than expanding these global defaults.
